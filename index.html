Unity IAP 和第三方内购

Posted on 2026-11-25 In Game Engine , Unity

Unity IAP

Unity IAP（In-App Purchasing）是 Unity 提供的内购工具包，让你通过一套 C# 接口接入不同平台的商店内购系统。
比如游戏里卖金币、去广告或订阅会员，都可以用它。它负责与商店交互；商品内容和购买后的游戏逻辑由你实现。

在 iOS 上，Unity IAP 调用 Apple StoreKit；在 Google Play 的 Android 应用上，调用 Google Play Billing。

支持的商品类型

商品类型 例子 特点
消耗型 Consumable 金币、钻石、体力 可以反复购买；发放与余额需要你自己管理
非消耗型 Non-Consumable 永久去广告、永久解锁关卡 通常购买一次，可以恢复购买
订阅 Subscription 月度会员、月度权益 在订阅有效期间提供权益，可能自动续费
注意“月卡”如何分类取决于设计：购买后获得 30 天奖励但不自动续费，与商店自动续订的月度会员，不是同一种购买机制。

购买流程

  1. 配置商品：在 App Store Connect、Google Play Console 中建立商品，并在游戏中配置对应的商品 ID。
  2. 连接商店并获取商品：读取商品是否可购买、当地价格、货币等信息。
  3. 玩家发起购买：Unity IAP 调用平台购买界面，由平台完成付款。
  4. 收到购买结果并验证：检查交易是否有效。
  5. 发放商品并确认交易：记录订单、增加金币或解锁权益，再向商店确认处理完成。
    价格展示应使用商店返回的本地化价格，例如HK$38.00，避免自己写死价格。
Unity IAP 提供的能力 你需要实现的业务
连接平台商店、获取商品信息 商品配置和商店 UI
发起购买、接收交易状态 验证交易、记录订单和发放奖励
提供交易凭证或相关数据 服务端校验与防止重复发货
接入恢复购买等平台能力 恢复对应权益、处理订阅状态变化

最需要注意的是：购买结果可能重复送达。 比如付款成功后游戏崩溃，下次启动时商店可能重新交付未处理的交易。
因此，发货逻辑应该根据交易 ID 去重，确保同一笔订单只发一次奖励。
对于有价值的金币、会员等商品，通常让服务端验证交易并保存发货记录。退款、订阅到期等变化，也需要相应更新玩家权益。

开发与测试

Unity IAP 负责接入购买流程，钱由对应商店收取，再结算给开发者。例如使用 Apple 内购时：

因此，你不是在 Unity IAP 代码里填写收款账号，而是在对应平台的开发者后台配置结算信息。
Unity IAP 主要负责获取商品、发起购买、接收交易结果等；游戏还需要验证订单、发放商品。

发布平台 常用接入方式
iOS App Store Unity IAP → Apple StoreKit
Android Google Play Unity IAP → Google Play Billing
Steam Steamworks SDK + 服务端微交易 API

Steam 的典型流程是：玩家点击购买 → 服务端创建交易 → Steam 界面让玩家授权钱包付款 → 服务端完成交易 → 游戏发放商品。收入由 Steam 按协议结算到 Steamworks 配置的银行账户。

可以通过 Package Manager 安装 In App Purchasing。开发时可以使用它提供的模拟商店能力检查购买流程，再通过 Apple 沙盒、TestFlight 或 Google Play 测试渠道验证真实平台行为。
Unity IAP 不同大版本的 API 差异较大，尤其 v4 与 v5 的初始化、回调和订单处理方式。 找教程时先确认版本，避免把不同版本的代码混用。

对 Unity 客户端开发来说，你可以把它理解为：统一调用商店的工具包
加上你自己实现的订单与商品发放系统，共同组成完整内购功能。

PayPal支付

Unity 应用通常通过“网页结账 + 服务端调用 PayPal API”接入 PayPal。这条流程可以独立于 Unity IAP 实现。

接入步骤

  1. 创建 PayPal 商家账户和开发者应用
    在 PayPal Developer 创建应用，获得 Client ID 和 Client Secret。先用 Sandbox 测试。
  2. 服务端创建订单
    Unity 把商品 ID 发给你的服务端。服务端查询商品价格，再调用 PayPal Orders v2 API 创建订单，返回结账链接。
  3. Unity 打开结账网页
    可以用 Application.OpenURL(checkoutUrl) 打开系统浏览器，让玩家完成 PayPal 授权。移动端可配置 Universal Link／App Link 或深链接返回游戏。
  4. 服务端完成扣款并发货
    玩家批准付款后，服务端调用 Capture Order 接口。确认捕获付款状态为 COMPLETED，并核对订单、金额、币种和玩家身份后，再发放商品。
    玩家跳回游戏、网页显示成功，都不能单独作为发货依据。
  5. Unity 查询结果
    返回游戏后，客户端向你的服务端查询订单状态，再刷新金币、会员等权益。玩家没有返回游戏时，服务端也应能够继续处理已批准的订单。

必须处理的订单问题

问题 处理方式
玩家重复点击购买 防止重复创建或重复扣款，使用幂等机制
API 结果或通知重复到达 根据订单和付款记录去重，同一笔付款只发货一次
付款后断网或关闭游戏 服务端保存状态，恢复后查询；用经过验证的 Webhook 补充同步
退款或争议 接收对应通知，按业务规则调整权益或订单状态

  1. 创建订单：同一次购买使用同一个请求 ID

注意：每次点击都生成新 ID，就不能防止重复点击产生多笔订单。 客户端还需要在购买处理中禁用按钮，并复用当前购买请求。

1. 层过滤：Layer Culling

不经过几何算法，直接使用规则过滤。例如某台相机只绘制场景层，不绘制特效层。实现上用位掩码判断：

不匹配的对象不进入这台相机的绘制范围。Unity 的 Camera.cullingMask 就是这个用途。
特点：判断便宜，但它并不分析对象 “实际看不看得见”，只是执行你指定的规则。

2. 距离剔除：Distance Culling

可以给不同类别设置不同距离：小装饰物近一些剔除，大建筑远一些剔除。
Unity 支持 Camera.layerCullDistances；其默认判断边界是与相机对齐的平面，也可以通过 layerCullSpherical 改成球形距离边界。

距离剔除通常属于画质与性能的主动取舍，需要考虑突然消失的视觉问题。它与视锥剔除的区别是：

  • 视锥剔除：这个对象位于当前可见范围之外。
  • 距离剔除：对象可能仍在视野里，但超过了允许显示的距离。

3. 视锥剔除：Frustum Culling

它判断对象的包围体是否位于相机视锥之外。通常测试包围球、AABB 或 OBB，而不是逐个三角形测试。包围体完全在外面才剔除；与视锥相交则保留。
对象多时，可以用 BVH、八叉树等层级结构：

测试父节点包围体
├─ 完全在外面 → 整棵子树跳过
├─ 完全在里面 → 子节点不用再做该视锥测试
└─ 与边界相交 → 继续测试子节点

BVH、八叉树不是另一种可见性判断规则，而是让剔除测试更高效的数据结构。

  1. PVS：Potentially Visible Set 预计算潜在可见集
  2. 把场景划分为多个空间区域（Cell）。
  3. 离线计算：从每个区域中，哪些其他区域可能可见。
  4. 保存这些集合。
  5. 运行时找到相机所在区域，只考虑对应 PVS 中的对象或区域。
  6. 对剩余对象继续做视锥等测试。

它保存的是可能可见，不一定是 “此刻确实可见”。例如某个房间从当前区域的某个位置能看到，就可能被保留。
优点：把复杂计算转移到离线阶段。
代价：需要存储数据，而且可见性依赖用于预计算的场景结构。Unity 传统烘焙式遮挡剔除也是先生成 Cell 与可见性数据，再在运行时查询；它允许动态对象被遮挡，但动态对象不能作为该烘焙系统的遮挡者。

绘制顺序和深度测试

Posted on 2026-11-23 Edited on 2026-11-24 In Game Engine , Unity
  • 绘制顺序：先画 A，还是先画 B。Unity 会根据排序层、渲染队列、距离等规则决定顺序。
  • 深度测试 ZTest：画到某个像素时，将它的深度与深度缓冲中已有的深度比较，决定是否允许绘制。常见的 LEqual 表示：比已有深度更近或相等才能通过。
  • 深度写入 ZWrite：这个对象是否更新深度缓冲。通常不透明物体开启，半透明物体关闭。关闭深度写入，不等于关闭深度测试。

所以，后画不一定能盖住先画的物体：如果先画的物体写入了更近的深度，后画的物体仍可能被深度测试拒绝。反过来，如果两个物体都不写深度，它们也不会仅凭 “谁更近” 就自动互相遮挡。

SpriteRenderer 绘制顺序

精灵渲染器控制绘制顺序通常优先使用：

  1. Sorting Layer：分组控制前后关系。
  2. Order in Layer：同一 Sorting Layer 内，值越大越晚画，通常显示在上面。
  3. 距离排序：在前面的排序条件相同时，距离可以决定顺序；透明精灵通常按远到近绘制。

所以，改变 SpriteRenderer 的 Z，确实可能改变绘制顺序，不只是影响深度测试。 不过距离排序还取决于 Transparency Sort Mode：

  • 正交排序：看沿相机视线方向的距离。
  • 透视排序：看排序点到相机位置的距离。
  • 自定义轴排序：按指定轴排序，比如按 Y 而不是 Z。

复杂角色由多个 Sprite 组成时，可以用 Sorting Group 将它们作为一组参与外部排序。

UGUI Image 绘制顺序

同一个 Canvas 内的绘制顺序：主要看 Hierarchy 顺序

在没有独立排序子 Canvas 的情况下，同级元素在 Hierarchy 中越靠下，越晚绘制，重叠时通常显示在上面。不是根据每个 Image 的 Z 从远到近排序。

不同 Canvas 之间：控制 Canvas 的排序

  • Screen Space - Overlay：主要使用 Canvas 的 Sort Order。
  • Screen Space - Camera / World Space：使用 Canvas 的 Sorting Layer 和 Order in Layer。
  • 嵌套的子 Canvas 想脱离父 Canvas 的排序，需要开启 Override Sorting。

Canvas 和 SpriteRenderer 之间

普通 Image 本身没有独立的 Sorting Layer／Order in Layer，这些属性属于 Canvas。
同一个 Canvas 内的 Image 共用 Canvas 的排序设置，因此修改 Canvas 的 Order，不会改变这些 Image 彼此的前后关系；内部主要按 Hierarchy 顺序绘制。

  • Screen Space - Overlay：在绘制完毕场景内其他对象之后绘制
    • 不参与场景透明对象的距离排序，而是覆盖在场景上方
    • 默认 UI Shader 在 Overlay 模式下使用 ZTest Always，不会因为场景物体更近而被深度测试挡住
  • Screen Space - Camera：通过项目里的同一套 Sorting Layer 和 Order in Layer 以及材质的 Render Queue，控制它与 SpriteRenderer 的绘制先后。
    • 前提是 Canvas 指定了 Render Camera，Sprite 也由同一相机绘制，使用常规透明材质，没有额外的自定义渲染 Pass；不同相机或者不同渲染阶段则不能靠Sorting Order。
    • Screen Space - Camera 与 Sprite 在同层、同 Order 时，不能把 Transparency Sort Mode 当成跨版本可靠的控制方式。
    • Unity 官方记录过：较新的部分版本中，即使 Sprite 放在 Canvas 平面前方，也仍画在 UI 后面；UI 与场景的距离交错存在版本相关行为，建议用不同的 Sorting Layer／Order 明确控制。
  • World Space：在同一相机、同一透明渲染阶段中，通常会继续比较 Sorting Layer → Order in Layer → 材质的 Render Queue → 排序距离 → 其他内部排序条件
    • 所以，如果层、Order、Render Queue 都相同，就可以通过设置透明排序模式影响 Sprite 与 World Space Canvas 的绘制顺序，通常远的先画、近的后画。
    • Transparency Sort Mode 控制的是透明排序中的距离比较方式；ZTest 则比较当前像素与此时深度缓冲中已有的深度，决定这个像素能否画出来。两者是独立的。
    • 在渲染此物体的相机／渲染管线的透明排序配置中设置，只会改变透明排序中 “距离” 的比较方式，不会取代 Sorting Layer／Order，也不会让同一个 Canvas 内的 Image 改为按距离排序
      • 内置渲染管线：Edit → Project Settings → Graphics → Transparency Sort Mode，也可以通过相机的 transparencySortMode API 设置。
      • URP 的 2D Renderer：在实际使用的 2D Renderer Data 资源 → General → Transparency Sort Mode 中配置，不是在 Canvas 上；该 Renderer 的配置会覆盖项目 Graphics 中的对应配置。
    • 注意这里说的是 Transparency Sort Mode（控制透明对象排序时，如何计算 “距离”），不要把它与相机的 Projection 混为一谈（控制画面如何投影）。
      • Orthographic：沿相机视线排序，比较对象沿相机视线方向的距离。常规 2D 相机朝世界 Z 轴看，所以主要由 Z 决定；如果相机旋转了，就不再只是比较世界 Z 值。
      • Perspective：按到相机位置的距离排序，比较对象排序点到相机位置的直线距离。因此，X、Y、Z 都可能影响排序距离；同一个 Z，不代表距离相同。
      • Custom Axis：沿自定义轴排序，例如指定 (0, 1, 0)，就按世界 Y 方向的位置比较，常用于俯视／等距 2D 场景；这时不需要靠 Z 区分前后。
      • Default：默认情况下，正交相机采用正交排序，透视相机采用透视排序；它不是第四种独立的距离计算方法。

Render Queue

在**常规 2D 透明对象排序中，Render Queue 在 Sorting Layer／Order 之后、距离之前决定顺序。**但它还有另一个作用：区分不透明、透明等渲染阶段。

  • 同一透明阶段内：层和 Order 相同时，比较 Queue；前面的条件已经分出先后，后面的条件就不能推翻它。
  • 跨不透明／透明阶段：Queue 决定进入哪一类绘制标准流程通常先处理不透明，再处理透明。常见 Queue 值包括
    • Geometry = 2000：不透明物体。
    • AlphaTest = 2450：镂空物体。
    • Transparent = 3000：透明混合物体。

Sprite绘制开销问题

在一个场景内有50个sprite同时绘制会有什么开销和问题？

同图集能减少纹理切换、帮助合批，但即使合成一次 Draw Call，重叠的 Sprite 仍然需要分别处理像素。透明 UI、粒子、Sprite 的重叠正是常见的 Overdraw 来源。

  • Draw Call：CPU 给 GPU 下了多少次绘制指令。
  • Overdraw：同一个屏幕像素，被反复处理了多少次。
    “一次提交 50 张图” 不等于 “只计算一张图”。

常见 Alpha Blend 透明渲染需要考虑前后顺序，通常不能像不透明物体那样，仅保留最前面的一层就完成绘制。
因此，多个 Sprite 重叠时，会增加片元着色、纹理采样和混合的工作量；覆盖面积大、重叠层数多、Shader 复杂时，更容易遇到 GPU 填充率或带宽瓶颈。

一组铺满屏幕、彼此叠加的半透明 Sprite，即使成功合批，仍要处理多层像素；一组很小、互不重叠的 Sprite，则没有同样的重叠负担。
所以，50 个不是关键，屏幕覆盖面积和重叠程度才是关键。

但这是 Shader 的设置，不是组件本身强制的；换自定义材质就可以改变。比如URP 的 Sprite-Lit-Default / Sprite-Unlit-Default，以 Unity 2022.3 对应源码为例，都是以下设置：

另外，贴图中 Alpha = 0 的透明留白也不天然免费：如果区域仍在绘制网格内，且未被裁剪或测试剔除，默认 Sprite-Unlit 的片元函数仍会采样纹理、返回颜色，并没有按 Alpha 自动 discard。

深度测试

默认UI Shader中，Overlay UI 不会被场景物体遮住；Camera 和 World Space UI 则可以。

Unity 在绘制 Canvas 前设置 unity_GUIZTestMode：Screen Space - Overlay 使用 Always，其他两种模式通常使用 LEqual。

  • Screen Space - Overlay：不因场景深度而失败，UI 绘制在场景画面之上。
  • Screen Space - Camera：UI 位于摄像机前的一个平面上，位置由 Plane Distance 决定，可以被前面的场景物体遮住。
  • World Space：UI 位于世界空间中，同样可以被前面的场景物体遮住。

深度测试比较的是：UI 当前片元的深度，与深度缓冲中同一屏幕位置已保存的深度。 LEqual 的含义是：在已有深度前方或同深度的片元通过，后方的失败。
以是重叠区域的 UI 片元测试失败，不是整个 Image 因为附近存在一个更近的 GameObject 就被跳过。

ZTest无法解决 UI 之间的 Overdraw，关键是 ZWrite Off：

默认 UI 会读取已有深度来判断自己能否显示，但不会把自己的深度写进去，供后面的 UI 做遮挡判断。

因此，场景中已经写深度的不透明物体，可以挡住 Camera / World Space UI；但默认 UI 之间，不能靠彼此写入深度来消除重叠绘制。 这也是多个 Image 叠加仍可能产生 Overdraw 的原因。
另外，“深度测试失败” 也不等于 Draw Call 没有提交：它发生在 GPU 绘制流程中；符合条件时 Early-Z 能提前拒绝片元，但并不是 CPU 自动跳过整个 UI 对象。

  • 一个 Draw Call 提交的是网格（“一批要绘制的图元”），被裁剪或剔除之后存活的三角形光栅化后生成片元，再做深度测试

穿透问题和碰撞检测

Posted on 2026-11-09 Edited on 2026-11-11 In Gameplay

游戏中的“穿透”通常有两种不同的问题：
物体在一次更新中直接越过障碍物，碰撞根本没有被检测到；或者碰撞已经被检测到，但物体仍然陷进了障碍物，甚至被挤到另一侧。

物体高速穿墙

物理引擎通常按固定时间间隔更新，而不是在每一个真实时间点都计算碰撞。

采用离散碰撞检测时，可以将问题理解为：物理引擎检查更新时刻的碰撞形状，却没有充分检查两次更新之间经过的路径。

上一次物理更新 下一次物理更新
● ──────────│墙│────────── ●
检查时没重叠 检查时也没重叠

虽然运动路径经过墙，但两个检查时刻都没有重叠，于是碰撞可能被漏掉。这通常叫 Tunneling，隧穿。

真正需要关注的是相对运动速度。两个物体迎面运动时，即使各自速度不算特别高，相对速度也可能很高。
旋转同样可能造成问题：长杆快速旋转时，杆的末端可以在一个物理步内跨过很远的距离。

一个实用的判断思路是：

当“每个物理步的相对位移”接近或超过“障碍物和运动物体在运动方向上的有效尺寸”时，离散检测漏碰撞的风险会明显增大。
这只是风险判断，不是严格的安全保证。斜向移动、旋转、形状和接触位置都会影响结果。

物体陷进障碍物

这属于另一个问题：碰撞求解不够及时、不够准确，或者运动方式绕过了求解过程。

多数实时物理引擎允许出现少量重叠，然后通过接触约束、速度修正和位置修正，让物体逐渐分离。因此，轻微的嵌入不一定代表检测失效。

严重嵌入通常与这些因素有关：

  • 外力或速度太大，接触约束来不及阻止运动。
  • 堆叠、关节或多处接触很复杂，求解迭代次数不足。
  • 相互接触的动态物体质量差距很大，求解更难稳定。
  • 脚本持续强行设置位置，把物体反复推入墙中。
  • 物体生成时就与场景重叠。
  • 碰撞体尺寸、形状或缩放不合理。

解决方案

方案 原理 适用场景 局限或代价
连续碰撞检测 CCD 检查运动过程中的碰撞，或预测接触 高速刚体、弹丸 增加计算开销，具体模式对旋转等情况支持不同
缩短物理步长 提高物理更新频率，减小每步位移 整体物理模拟 CPU 开销增加，极高速物体仍可能穿透
增加子步 将一次运动拆成多次，每次都检测碰撞 快速角色、机关、复杂运动 子步越多，开销越大
射线检测 检查当前位置到预计下一位置的线段 小子弹、瞬时射击 射线没有厚度，不适合直接代表大物体
形状扫掠 用球、胶囊或盒子检查运动路径 有体积的弹丸、角色 需要处理初始重叠、多次碰撞和旋转

调整碰撞求解参数 提高接触约束的求解精度 堆叠下陷、关节拉伸、持续嵌入 无法解决根本没检测到的碰撞
改变对象实现方式 用命中查询或逻辑轨迹替代高速实体 枪械、飞行弹丸 需要自行实现飞行、命中和表现逻辑

这里有几个容易混淆的地方。

射线和形状扫掠虽然可以替代引擎内置 CCD，但沿运动路径检测碰撞，本身也属于连续检测的思路。
如果你想找原理上不同于 CCD 的办法，主要是缩短步长、增加离散子步、限制速度、调整碰撞体，以及重叠修正。

增加子步必须包含检测。
例如把一次移动拆成十次，每次都查询碰撞才有意义；只在循环里设置十次位置，物理引擎未必会在中间进行检测。

提高求解迭代次数主要解决“碰到了却挡不稳”。
它适合箱子堆叠、复杂接触等情况，不能解决子弹直接跳过薄墙造成的漏检测。

实际选择可以按对象来定：

  • 小子弹：检查前后位置之间的射线；需要飞行时间时，逐步计算轨迹并查询。
  • 火球、炮弹等有体积的弹丸：使用球形扫掠，或者适合的 CCD。
  • 玩家角色：移动前做胶囊查询，截断位移，再处理沿墙滑动和重叠恢复。
  • 动态箱子：检查移动方式和碰撞体，再按需要调整步长、CCD 和求解参数。
  • 快速挥剑、旋转刀片：采样旋转轨迹或检测扫掠体积，单纯检查中心移动路径不够。
  • 传送后卡进墙里：先验证目标位置，再做必要的重叠恢复。

通常会组合使用。例如角色采用 移动前形状查询＋沿墙滑动＋重叠恢复；高速弹丸采用 轨迹查询＋首次命中处理。

Spine 动画

Posted on 2026-11-05 In Animation

Spine 动画通常是在 Spine 编辑器里，把分层图片绑定到骨骼，再给骨骼和图片属性制作关键帧得到的。
Unity 通过 Spine 官方运行库播放它，它和 Unity 的 Animation / Animator 可以配合使用。

动画制作

以一个 2D 人物为例，用Spin制作动画通常是下面这个流程：

  1. 准备分层图片
    把头、身体、上臂、前臂、腿、武器等拆成独立图片。被其他部位遮住的部分通常也需要补画，避免转动时露出空洞。
  2. 在 Spine 编辑器中建立骨骼
    例如：身体 → 上臂 → 前臂 → 手。移动上臂时，前臂和手会跟着移动。
  3. 把图片挂到骨骼上
    简单部位可以直接挂一张图片；需要弯曲的部位，可以把图片划分成网格，并设置骨骼权重，让多个骨骼共同控制图片变形。
  4. 制作动画关键帧
    在时间轴上设置骨骼的位置、旋转、缩放，还可以设置图片切换、透明度、绘制顺序和网格变形，制作 idle、walk、attack 等动画。
  5. 导出供游戏使用的资源
    资源 用途
    .json 或 .skel 骨骼、皮肤、动画等数据
    .atlas 图片在图集中的位置和相关信息
    .png 实际显示的图集图片

所以它通常不是预先渲染的一段视频，也不是每帧一张图片。游戏运行时，Spine 根据动画数据计算骨骼姿态，再生成和绘制网格。

先安装官方 spine-unity 运行库。运行库版本要与导出资源所用的 Spine 编辑器主次版本匹配，例如 Spine 4.2 导出的资源，应使用对应的 4.2 运行库。

MipMap

Posted on 2026-10-28 Edited on 2026-10-29 In Graphics

MipMap（多级纹理映射）是计算机图形学中用于提高渲染效率和图像质量的一种技术。在Unity 3D等游戏开发中，MipMap的作用主要体现在以下几个方面：

  • 减少模糊效果：当纹理在屏幕上缩小时，使用MipMap可以避免出现模糊和失真现象。MipMap的概念是为同一纹理创建多个采样级别，每个级别的分辨率逐渐降低。当物体离摄像机较远时，使用较低分辨率的纹理进行渲染，从而提供更清晰、自然的视觉效果。
  • 提高渲染效率：通过选择合适的MipMap级别，可以减少显存带宽的使用。这是因为较低分辨率的纹理占用的内存较少，传输到显卡时也能够更快速，从而提高渲染速度。
  • 减少锯齿现象：MipMap有助于减少远景物体的锯齿效果。当物体距离摄像机较远时，使用低分辨率的MipMap纹理能够更自然地显示物体的轮廓。
  • 支持纹理过滤：MipMap通常和各种纹理过滤技术（如双线性、三线性过滤）结合使用，进一步改善渲染质量。

在Unity中，开发者可以在材质的设置中开启MipMap，系统会自动为指定的纹理生成适当的MipMap级别，从而优化游戏的表现。总之，MipMap在Unity 3D中的作用是提高画面质量和渲染性能，使游戏体验更加流畅和真实。

纹理采样

我们对纹理采样进行显示的过程，可以理解为将屏幕上的一个像素（下文用像素表示）映射到纹理上的一个像素（下文用纹素表示），然后用纹理上的这个像素的颜色进行显示。

理想情况下，屏幕上的每个像素都可以正好对应到纹理上的一个纹素。

如上图这种情况，将3X3的纹理显示到3X3的屏幕上时，屏幕坐标（1，1）的像素对应的正好也是纹理上（1，1）的纹素。
图中黑点代表的是每个纹素的位置，红点代表的是屏幕像素映射到纹理上的位置（uv），此时只需要取对应纹素的颜色进行显示即可。

  • 这里的 UV 通常指归一化坐标，一般在 [0, 1] 范围内，可以理解为百分比位置，但实际用小数表示。例如 (0.5, 0.5) 表示纹理中心。它不是直接的纹素坐标。
  • 对于宽 W、高 H 的纹理：UV (u, v) 对应纹素空间的位置为 (u × W, v × H)。

但在实际情况中，纹理采样的范围与显示该纹理的屏幕范围并不是一一对应的；
并且在透视相机下，随着纹理所附着的物体与摄像机间的距离改变，其占据的屏幕空间的大小也会发生变化，也就是纹理覆盖的屏幕区域的大小会发生变化。这就会出现纹理过小和纹理过大两种情况。

纹理过小

当物体靠近透视相机，占据的屏幕空间变大，屏幕上更大范围的像素会被用来显示物体身上的纹理，就会出现纹理过小的情况。

比如上图3X3的纹理需要显示在6X6的屏幕范围上时，图中红点和黄点分别代表屏幕空间的前两个像素，此时二者都对应纹理空间的第一个纹素，且其采样位置也不是正好在纹素的位置。
可见，纹理过小时会出现多个像素拥挤到同一个纹理像素上，并且纹理与屏幕范围差距越大，拥挤到同一个纹素上的像素数量越多。此时可以采用：

  • 就近点采样（最近邻采样）：根据 UV 选择最近的纹素中心，返回它的颜色。
  • 双线性过滤：混合周围几个纹素的颜色。

就近点采样



如上图所示，红点为屏幕像素映射到的位置，当使用就近点采样进行滤波时，会查找距离目标最近的纹素进行采样，也就是图中的蓝点对应的纹素。

就近点采样速度快，但问题也很明显，当纹理过小且纹理与屏幕范围差距较大时，如果采用就近点采样，就会导致大片的像素都采样到同一个颜色，使渲染出来的图像看起来一块一块的，颗粒感（或像素化）严重。

双线性插值



在双线性插值中，会考虑离采样点最近的四个纹素作为参考点，也就是上图中P1 P2 P3 P4四个蓝点
根据采样点与参考点的水平距离，对P1 P2进行插值得到新参考点P5的颜色、对P3 P4进行插值得到新参考点P6的颜色



之后根据采样点与参考点之间的纵向距离对新参考点P5P6进行插值，从而得到最终的采样颜色。

双线性插值通过两次插值计算，使采样结果在一定程度上反映出采样点附近的综合颜色，且速度也较快，是最常用的滤波方式。

纹理过大

当物体远离透视相机，占据的屏幕空间变小，物体身上的纹理只能被显示在屏幕上很少的几个像素上，就会出现纹理过大的情况。

当出现纹理过大时，如将6X6的纹理显示在4X4的屏幕范围内，一个屏幕像素内就需要塞下多个纹素，上图中红框和黄框分别代表相邻的2个屏幕像素对应的纹素范围。

由于一个像素无法包含如此多的颜色，因而会导致纹理信息丢失，并进一步导致相邻像素间颜色信息不连贯，从而产生摩尔纹或者锯齿化的现象（采样不足产生的混叠现象）。

  • 锯齿：斜线或物体边缘呈阶梯状。屏幕像素数量有限，无法准确表达连续的边界；物体移动时，边缘还可能闪烁
  • 摩尔纹：密集的重复图案出现原本不存在的条纹、波纹。例如远处的砖墙、格子地板，看起来产生大块明暗条带，移动时也可能闪烁

Mipmap

纹理过大问题的本质是一个像素无法表达多个纹素而导致的颜色信息丢失。
最直观的解决方案便是对单个屏幕像素覆盖的多个纹素进行多次采样，然后按照取平均值或者其他方式进行合并，以最终的合并结果作为采样得到的颜色值，也就是超采样技术。

实时超采样的开销无疑是巨大的，为了提升采样速度，我们可以按照一定范围将纹素提前进行合并，生成一张新的纹理，当需要进行超采样时，只要对新生成的纹理直接采样显示即可。
另外一个问题是，当物体与透视相机的距离发生改变，单个屏幕像素要表达的纹素数量也会发生变化，为了使采样结果更加可靠，我们可以以像素覆盖纹素的数量作为依据划分几个等级，计算每个等级需要合并的纹素范围，生成多张新纹理，在渲染时选择对应等级的新纹理进行采样。

以上便是MipMap的原理。

在MipMap中，以原始纹理作为Level 0。
将当前Level D的相邻四个像素进行合并，生成次一级的纹理Level D + 1。所以 Mipmap 每升一级，宽和高都减半。
在渲染时，根据相邻屏幕像素的UV坐标最大距离，算出每个屏幕像素覆盖的纹素范围L，然后对 L 取以 2 为底的对数即可得到对应的MipMap等级D。
最后从已经提前生成的Level D级的纹理中进行采样。

Google Protobuf

Posted on 2026-10-27 Edited on 2026-11-03 In Networks

Google Protocol Buffers（简称 Protobuf）是一套“数据结构定义 + 代码生成 + 二进制序列化”工具。
先在 .proto 文件里约定字段，再生成 C#、Java、Go 等语言的读写代码，让客户端和服务端遵守同一份协议。

数据定义

以这份玩家数据为例：

不带空格的 UTF-8 JSON 是 34 字节。
JSON 是文本格式，字段名、数值、字符串以及标点，最终都编码成文本字节传输。

比如 {“chips”:150} 的chips字段，除了字段名本身，还需要两个字节传输引号。 连同冒号，”chips”: 共占 8 字节。

这里 150 是 JSON 数值，占 3 字节。
接收方解析后，才会把数值文本 150 转换为内存中的数字；它在 JSON 传输时并不是一个固定 4 字节的整数。
类似地，12.5 传的是四个字符 1、2、.、5，JSON 本身也不区分 float 和 double，由接收程序决定怎么存储。

你的protobuf数据可以定义为：

这里的 1、2、3 是固定的字段编号，不是字段值。

按上面的协议，Protobuf 二进制通常只需要 8 字节：

内容 JSON Protobuf
字段标识 每次发送 "chips" 等字段名 发送字段编号和编码类型组成的标签
整数 150 3 个文本字节 2 个变长整数字节
浮点数 12.5 文本表示 float 固定 4 字节
bonus = 0 仍包含字段名和值 此例中，proto3 默认值省略
结构 花括号、引号、冒号、逗号 无须这些文本符号

这个例子里的 8 字节，chips 占 3 字节，money 占 5 字节，bonus 不占空间。（每个字段标签占1字节）
Protobuf的标签不包含字段名，也不一定直接包含字段长度。标签包含这个字段的部分元数据：字段编号和底层编码方式。

整条消息的结束位置则由外层提供，例如 HTTP 响应体的长度或嵌套消息的长度前缀。Protobuf 本身没有一个通用的“消息结束符”，所以在连续的 TCP 字节流中发送多条消息时，需要另外约定每条消息的长度。

数据结构

字段编号与字段名的对应关系需要额外存储。
Protobuf 的关键是：把这份映射提前放在客户端和服务端的协议定义、生成代码里，而不是每次发送数据时重复传输。

所以它用“双方提前约定数据结构”的成本，换取“每条消息更小”的收益。

但缩小比例取决于数据：大量重复字段名、数字、列表通常收益明显；很长的字符串内容仍然要传。
Protobuf 不是压缩算法，也不是加密算法，还可以与 gzip 等压缩一起使用。
若用 Protobuf 的 JSON 输出模式，传输的仍是 JSON，拿不到上述二进制收益。

接入时需要注意这几件事：

  1. 客户端和服务端共同支持协议。 如果服务端仍然只接受表单和 JSON，单独换 Unity 序列化方式无法使用。
  2. 网络层改为处理字节。 通常用 UploadHandlerRaw 发送，读取 downloadHandler.data 接收；Protobuf 也可以继续通过普通 HTTP 使用，不要求 gRPC。
  3. Unity 可以使用 Google.Protobuf，但接入后仍需验证程序集引用和目标平台的 IL2CPP 构建

字段映射

开发时，.proto 文件就是协议定义：

字段编号 字段名 数据类型
1 chips int32
2 money float
3 bonus float

通过 protoc 编译器，可以为客户端生成 C# 类，为服务端生成对应语言的类。

字段名还可能保存在生成的描述信息中，用于反射、JSON 转换等功能。这些内容属于程序代码和元数据，不需要跟着每条网络消息发送。
可以理解为双方事先约定：

“编号 1 表示筹码，编号 2 表示余额，编号 3 表示奖励余额。”

此后每次通信只发送“编号和值”。

JSON 则会在每次通信时重复发送：

“chips 的值是 150，money 的值是 12.5……”

因此，Protobuf 并没有消灭映射，而是把映射从每条消息里移到了双方程序里。

以及二进制里并不是只有字段值，Protobuf 不能直接把 150 和 12.5 连起来，因为接收方需要知道：

  • 这是哪个字段？
  • 这个字段的值占多少字节？
  • 读完后下一个字段在哪里？

所以每个实际发送的字段，基本结构是：

字段标签 tag + 字段值

对于字符串等可变长度的数据，则是：

字段标签 tag + 内容长度 + 内容

Unity热更新

Posted on 2026-08-20 Edited on 2026-11-03 In Game Engine , Unity

Unity热更新可以通过Lua框架（xLua, toLua等）或者HybridCLR实现。

xLua 下载的是 Lua 脚本，由 Lua VM 执行。
HybridCLR 下载的是 C# DLL，由 HybridCLR 在 IL2CPP 中解释执行。

主要流程

如果你项目使用 Addressables，那么 catalog.json、AB 包、New Build / Update Build 的流程，对两者都一样。
Addressables 不关心文件是 Lua 还是 DLL；它只负责把指定地址的资源拿回来。

Player 内置启动器
↓
检查远端 catalog.hash / catalog.json
↓
下载变化的 AssetBundle
↓
从 AB 取出热更新文件
↓
加载并运行热更新逻辑

首次发布Android平台远端资源时，可以这样做：

Addressables → New Build
↓
ServerData/Android/
↓
将其中内容部署到 Cloudflare/CDN 的 Android 资源目录

例如：

本地：
ServerData/Android/
catalog_xxx.json
catalog_xxx.hash
hotcode_a1.bundle
ui_b1.bundle

CDN：
https://assets.example.com/aa/Android/
catalog_xxx.json
catalog_xxx.hash
hotcode_a1.bundle
ui_b1.bundle

需要确保以下两点：

  1. 指定远端资源构建。需要启用 Build Remote Catalog，并将需要热更的 Group 设置为：

Build Path = Remote.BuildPath
Load Path = Remote.LoadPath

仅在当前项目点击 New Build，因远端 Catalog 关闭、默认 Group 是 Local，未必会产生可部署的 ServerData/Android 完整热更新内容。

  1. Remote.LoadPath 必须在构建前指向真实 CDN 地址，例如：

https://assets.example.com/aa/[BuildTarget]

不要先用 localhost 构建，再直接把文件传到 Cloudflare；Catalog 中会保留构建时写入的 LoadPath。

首次发布后，后续的操作不同：

Update Previous Build
↓
只产生新增/变化的 Bundle 与新 Catalog
↓
合并到服务器已有 Android 资源目录

不要清空服务器 Android 目录，也不要只部署本次 Update Build 的少量输出。新 Catalog 文件替换，旧 Bundle 保留。

xLua：Lua 驱动 C#

xLua 的核心是把 Lua VM 放进 Player：

C# AOT Player
↓
LuaEnv
↓
下载 Main.lua、Login.lua、Battle.lua
↓
Lua 脚本解释执行
↓
通过绑定层调用 Unity/C#

游戏启动时，C# 通常创建一个全局 LuaEnv
所以它不是“把 Lua 脚本编译进原生 Player”；而是 Player 预先带着 Lua 解释器，后续下载 Lua 脚本，解释器负责运行这些新脚本。

Lua 与 C# 的交互通常需要配置生成：

  • CSharpCallLua：让 C# 调用 Lua。
  • LuaCallCSharp：让 Lua 高效调用 C#。
  • Delegate、Interface、泛型、重载等都要处理绑定与代码生成。

xLua 的两种“热更新”

  • Lua 业务热更新
    这是最常见、最稳的方式：

C#：框架、Unity 封装、网络、资源管理
Lua：UI 流程、活动、战斗规则、业务逻辑

后续下载新的 Lua 文件即可生效。
优点是包小、更新快；代价是业务层需要长期使用 Lua 开发，并维护 Lua/C# 边界。

  • xLua Hotfix：Lua 覆盖 C# 方法
    xLua 还有 Hotfix 注入机制。你在发包前标记/生成可热修复的 C# 方法，构建时 xLua 向这些方法插入跳板：

原 C# 方法
↓
预先注入 Hotfix 检查点
↓
运行时 Lua 可替换该方法实现

例如 Lua 可以通过 xlua.hotfix(…) 替换一个已预留的 C# 方法。
关键限制是：xLua 不能在 Player 发布后，任意修改一个当初没有注入 Hotfix 跳板的 C# 方法。
也就是说，它是“预埋可替换点”，不是发布后任意加载新 C# 代码。

HybridCLR：运行新的 C# 逻辑

HybridCLR 则更接近“可加载新的 C# 程序集”，但同样受基础 Player 的 API、裁剪、泛型、桥接代码约束。

C# AOT Player
↓
HybridCLR Runtime
↓
下载 Game.HotUpdate.dll.bytes
↓
Assembly.Load
↓
解释执行新的 C# IL

热更新代码仍是 C#：

  • 可以新增普通 C# 类、接口、业务系统。
  • 可以使用熟悉的 C# 语法、async、LINQ、泛型、异常等。
  • 可以直接引用已有 AOT 层 API。
  • 主体逻辑通常无需改写成另一种语言。
    但它不能改变已经编译进 Player 的原生 AOT 代码；它解决的是“新增/替换热更新程序集中的逻辑”。

Catalog 与 AB包

假设热更入口地址为 HotEntry。

  • xLua

catalog.json
“HotEntry”
→ lua_main_abc.bundle

lua_main_abc.bundle
→ Main.lua
→ Login.lua
→ Battle.lua

运行时：

  • HybridCLR

catalog.json
“HotEntry”
→ hotcode_abc.bundle

hotcode_abc.bundle
→ Game.HotUpdate.dll.bytes

运行时：

HybridCLR 可能还多一组

aotmetadata_abc.bundle
→ Game.Runtime.dll.bytes
→ System.dll.bytes

这些 AOT 元数据要在加载热更新 DLL 前处理。

New Build / Update Build 对比

它们的发布方式一致。第一次发包：

xLua：
New Build → Lua AB + Catalog → 打入/上传

HybridCLR：
生成 HybridCLR 必要代码
→ 构建 Player
→ 打包热更新 DLL / AOT 元数据到 AB
→ New Build → Catalog + AB

后续只改热更逻辑：

xLua：
改 Lua → Update Previous Build → 上传新 Lua AB + Catalog

HybridCLR：
编译新 HotUpdate.dll
→ Update Previous Build
→ 上传新 DLL AB + Catalog

两者都不是二进制增量补丁：

  • 修改一个 Lua 文件，通常重下它所在的整个 Lua Bundle。
  • 修改一个 DLL，通常重下它所在的整个 DLL Bundle。
  • Bundle 划分越细，下载越小；Bundle 越大，依赖和管理越简单。

unity 计算点到直线距离

Posted on 2026-08-07 In Game Engine , Unity

点到直线距离

方法一：投影 + 勾股定理

利用点到直线上某点的向量长度，以及它在直线方向上的投影长度，用勾股定理求出垂直分量。

原理：|d|² = |斜边|² - |投影|²（勾股定理）。

注意：在浮点误差下 sqrMagnitude - fProj² 可能出现极小的负数，导致 Mathf.Sqrt 返回 NaN，必要时可对被开方数做一次 Mathf.Max(0, ...) 保护。

方法二：叉乘（面积法）

两向量叉乘的模等于它们所构成平行四边形的面积，面积除以底边长度即为高（也就是点到直线的距离）。这种方式在 3D 中最推荐，代码简洁且数值稳定。

原理：距离 = 平行四边形面积 / 底 = |v × dir| / |dir|。

方法三：先求投影点，再求两点距离

先算出点在直线上的投影点坐标，再直接用 Vector3.Distance。好处是能顺便拿到最近点（投影点）。

补充：以上三种求的都是无限长直线的距离。如果要的是**线段（Segment）**距离，需要把投影参数 t 用 Mathf.Clamp01 限制在 [0, 1] 之间，再求点到该最近点的距离。

点到面距离

点到平面的距离公式：d = |Ax0 + By0 + Cz0 + D| / √(A² + B² + C²)。

平面的一般式方程为 Ax + By + Cz + D = 0，平面的法向量为 (A, B, C)。

如果一个非零向量 n 与平面 a 垂直，则称向量 n 为平面 a 的法向量。垂直于平面的直线所表示的向量即为该平面的法向量。每一个平面存在无数个法向量。

方法一：用 Plane 类

Unity 内置的 Plane 类可以由三点构造，并直接求点到平面的（有符号）距离。

方法二：用法线 + 点乘

由平面上两条边叉乘得到法向量，再把「点到平面上一点」的向量投影到法向量方向上，其绝对值即为距离。
