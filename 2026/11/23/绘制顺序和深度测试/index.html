绘制顺序和深度测试

Posted on 2026-11-23 Edited on 2026-11-24 In Game Engine , Unity Views:
  • 绘制顺序：先画 A，还是先画 B。Unity 会根据排序层、渲染队列、距离等规则决定顺序。
  • 深度测试 ZTest：画到某个像素时，将它的深度与深度缓冲中已有的深度比较，决定是否允许绘制。常见的 LEqual 表示：比已有深度更近或相等才能通过。
  • 深度写入 ZWrite：这个对象是否更新深度缓冲。通常不透明物体开启，半透明物体关闭。关闭深度写入，不等于关闭深度测试。

所以，后画不一定能盖住先画的物体：如果先画的物体写入了更近的深度，后画的物体仍可能被深度测试拒绝。反过来，如果两个物体都不写深度，它们也不会仅凭 “谁更近” 就自动互相遮挡。

SpriteRenderer 绘制顺序

精灵渲染器控制绘制顺序通常优先使用：

  1. Sorting Layer：分组控制前后关系。
  2. Order in Layer：同一 Sorting Layer 内，值越大越晚画，通常显示在上面。
  3. 距离排序：在前面的排序条件相同时，距离可以决定顺序；透明精灵通常按远到近绘制。

所以，改变 SpriteRenderer 的 Z，确实可能改变绘制顺序，不只是影响深度测试。 不过距离排序还取决于 Transparency Sort Mode：

  • 正交排序：看沿相机视线方向的距离。
  • 透视排序：看排序点到相机位置的距离。
  • 自定义轴排序：按指定轴排序，比如按 Y 而不是 Z。

复杂角色由多个 Sprite 组成时，可以用 Sorting Group 将它们作为一组参与外部排序。

UGUI Image 绘制顺序

同一个 Canvas 内的绘制顺序：主要看 Hierarchy 顺序

在没有独立排序子 Canvas 的情况下，同级元素在 Hierarchy 中越靠下，越晚绘制，重叠时通常显示在上面。不是根据每个 Image 的 Z 从远到近排序。

不同 Canvas 之间：控制 Canvas 的排序

  • Screen Space - Overlay：主要使用 Canvas 的 Sort Order。
  • Screen Space - Camera / World Space：使用 Canvas 的 Sorting Layer 和 Order in Layer。
  • 嵌套的子 Canvas 想脱离父 Canvas 的排序，需要开启 Override Sorting。

Canvas 和 SpriteRenderer 之间

普通 Image 本身没有独立的 Sorting Layer／Order in Layer，这些属性属于 Canvas。
同一个 Canvas 内的 Image 共用 Canvas 的排序设置，因此修改 Canvas 的 Order，不会改变这些 Image 彼此的前后关系；内部主要按 Hierarchy 顺序绘制。

  • Screen Space - Overlay：在绘制完毕场景内其他对象之后绘制
    • 不参与场景透明对象的距离排序，而是覆盖在场景上方
    • 默认 UI Shader 在 Overlay 模式下使用 ZTest Always，不会因为场景物体更近而被深度测试挡住
  • Screen Space - Camera：通过项目里的同一套 Sorting Layer 和 Order in Layer 以及材质的 Render Queue，控制它与 SpriteRenderer 的绘制先后。
    • 前提是 Canvas 指定了 Render Camera，Sprite 也由同一相机绘制，使用常规透明材质，没有额外的自定义渲染 Pass；不同相机或者不同渲染阶段则不能靠Sorting Order。
    • Screen Space - Camera 与 Sprite 在同层、同 Order 时，不能把 Transparency Sort Mode 当成跨版本可靠的控制方式。
    • Unity 官方记录过：较新的部分版本中，即使 Sprite 放在 Canvas 平面前方，也仍画在 UI 后面；UI 与场景的距离交错存在版本相关行为，建议用不同的 Sorting Layer／Order 明确控制。
  • World Space：在同一相机、同一透明渲染阶段中，通常会继续比较 Sorting Layer → Order in Layer → 材质的 Render Queue → 排序距离 → 其他内部排序条件
    • 所以，如果层、Order、Render Queue 都相同，就可以通过设置透明排序模式影响 Sprite 与 World Space Canvas 的绘制顺序，通常远的先画、近的后画。
    • Transparency Sort Mode 控制的是透明排序中的距离比较方式；ZTest 则比较当前像素与此时深度缓冲中已有的深度，决定这个像素能否画出来。两者是独立的。
    • 在渲染此物体的相机／渲染管线的透明排序配置中设置，只会改变透明排序中 “距离” 的比较方式，不会取代 Sorting Layer／Order，也不会让同一个 Canvas 内的 Image 改为按距离排序
      • 内置渲染管线：Edit → Project Settings → Graphics → Transparency Sort Mode，也可以通过相机的 transparencySortMode API 设置。
      • URP 的 2D Renderer：在实际使用的 2D Renderer Data 资源 → General → Transparency Sort Mode 中配置，不是在 Canvas 上；该 Renderer 的配置会覆盖项目 Graphics 中的对应配置。
    • 注意这里说的是 Transparency Sort Mode（控制透明对象排序时，如何计算 “距离”），不要把它与相机的 Projection 混为一谈（控制画面如何投影）。
      • Orthographic：沿相机视线排序，比较对象沿相机视线方向的距离。常规 2D 相机朝世界 Z 轴看，所以主要由 Z 决定；如果相机旋转了，就不再只是比较世界 Z 值。
      • Perspective：按到相机位置的距离排序，比较对象排序点到相机位置的直线距离。因此，X、Y、Z 都可能影响排序距离；同一个 Z，不代表距离相同。
      • Custom Axis：沿自定义轴排序，例如指定 (0, 1, 0)，就按世界 Y 方向的位置比较，常用于俯视／等距 2D 场景；这时不需要靠 Z 区分前后。
      • Default：默认情况下，正交相机采用正交排序，透视相机采用透视排序；它不是第四种独立的距离计算方法。

Render Queue

在**常规 2D 透明对象排序中，Render Queue 在 Sorting Layer／Order 之后、距离之前决定顺序。**但它还有另一个作用：区分不透明、透明等渲染阶段。

  • 同一透明阶段内：层和 Order 相同时，比较 Queue；前面的条件已经分出先后，后面的条件就不能推翻它。
  • 跨不透明／透明阶段：Queue 决定进入哪一类绘制标准流程通常先处理不透明，再处理透明。常见 Queue 值包括
    • Geometry = 2000：不透明物体。
    • AlphaTest = 2450：镂空物体。
    • Transparent = 3000：透明混合物体。

Sprite绘制开销问题

在一个场景内有50个sprite同时绘制会有什么开销和问题？

同图集能减少纹理切换、帮助合批，但即使合成一次 Draw Call，重叠的 Sprite 仍然需要分别处理像素。透明 UI、粒子、Sprite 的重叠正是常见的 Overdraw 来源。

  • Draw Call：CPU 给 GPU 下了多少次绘制指令。
  • Overdraw：同一个屏幕像素，被反复处理了多少次。
    “一次提交 50 张图” 不等于 “只计算一张图”。

常见 Alpha Blend 透明渲染需要考虑前后顺序，通常不能像不透明物体那样，仅保留最前面的一层就完成绘制。
因此，多个 Sprite 重叠时，会增加片元着色、纹理采样和混合的工作量；覆盖面积大、重叠层数多、Shader 复杂时，更容易遇到 GPU 填充率或带宽瓶颈。

一组铺满屏幕、彼此叠加的半透明 Sprite，即使成功合批，仍要处理多层像素；一组很小、互不重叠的 Sprite，则没有同样的重叠负担。
所以，50 个不是关键，屏幕覆盖面积和重叠程度才是关键。

因此，Alpha = 1 只是混合结果完全覆盖背景，不会自动把 Blend 关闭，也不会把 ZWrite Off 改成 On。也就是说，“看起来不透明” 不等于 “使用不透明渲染路径”。
这就解释了之前的隐患：一个完全不透明的默认 Image / Sprite 盖在其他元素上，并不意味着下面的元素会自动免于绘制。 重叠元素仍可能产生片元计算和混合开销，即使它们已经合批。
另外，贴图中 Alpha = 0 的透明留白也不天然免费：如果区域仍在绘制网格内，且未被裁剪或测试剔除，默认 Sprite-Unlit 的片元函数仍会采样纹理、返回颜色，并没有按 Alpha 自动 discard。

深度测试

默认UI Shader中，Overlay UI 不会被场景物体遮住；Camera 和 World Space UI 则可以。

Unity 在绘制 Canvas 前设置 unity_GUIZTestMode：Screen Space - Overlay 使用 Always，其他两种模式通常使用 LEqual。

  • Screen Space - Overlay：不因场景深度而失败，UI 绘制在场景画面之上。
  • Screen Space - Camera：UI 位于摄像机前的一个平面上，位置由 Plane Distance 决定，可以被前面的场景物体遮住。
  • World Space：UI 位于世界空间中，同样可以被前面的场景物体遮住。

深度测试比较的是：UI 当前片元的深度，与深度缓冲中同一屏幕位置已保存的深度。 LEqual 的含义是：在已有深度前方或同深度的片元通过，后方的失败。
以是重叠区域的 UI 片元测试失败，不是整个 Image 因为附近存在一个更近的 GameObject 就被跳过。

ZTest无法解决 UI 之间的 Overdraw，关键是 ZWrite Off：

默认 UI 会读取已有深度来判断自己能否显示，但不会把自己的深度写进去，供后面的 UI 做遮挡判断。

因此，场景中已经写深度的不透明物体，可以挡住 Camera / World Space UI；但默认 UI 之间，不能靠彼此写入深度来消除重叠绘制。 这也是多个 Image 叠加仍可能产生 Overdraw 的原因。
另外，“深度测试失败” 也不等于 Draw Call 没有提交：它发生在 GPU 绘制流程中；符合条件时 Early-Z 能提前拒绝片元，但并不是 CPU 自动跳过整个 UI 对象。

  • 一个 Draw Call 提交的是网格（“一批要绘制的图元”），被裁剪或剔除之后存活的三角形光栅化后生成片元，再做深度测试
