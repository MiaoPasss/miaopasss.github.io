Post processing 和 Volume profile

Posted on 2026-11-26 In Game Engine , Unity Views:

0. 参数：Volume Profile

Volume Profile 是配置资产，不是渲染出来的图像，也不会自己执行效果。
它保存 Bloom、色彩调整、景深等配置，例如 Bloom 的 Threshold、Intensity、Scatter。

场景中的 Volume 引用这个 Profile，并决定它如何影响相机：

  • Global：没有空间边界。
  • Local：根据相机位置和空间范围产生影响。
  • Weight、Priority：参与多个 Volume 的参数混合。

URP 据此计算出当前相机最终使用的一组效果参数。所以你编辑的是某份 Profile，实际执行时使用的可能是多个 Volume 混合后的结果。

SRP 和 Built-in

  • SRP 是可编程渲染管线框架；URP 和 HDRP 是 Unity 基于它编写好的、开箱即用的管线实现。 两者都使用了 Volume + VolumeProfile，保存 VolumeComponent 配置。
  • Built-in 没有内置接入这套 VolumeProfile 效果处理流程。 它常用的 Post-processing Stack v2 是另一套系统，使用 PostProcessVolume 和 PostProcessProfile。

严格来说，VolumeProfile 本身只是一个保存参数的 ScriptableObject，自定义代码也可以读取它；真正的限制是渲染系统是否实现了对应效果，而 Built-in 不会自动读取其中的配置并执行对应效果。

1. 读取贴图和材质，在线性空间计算

常见颜色贴图是 sRGB 编码。在 Linear 工作流程中，标记为 sRGB 的贴图被采样时，会解码成线性值，再参与 Shader 计算；已经是线性数据的纹理不需要重复解码。
例如，sRGB 的 (0.5) 对应线性值约 (0.214)，而 sRGB 的 1 对应线性值仍然是 1。同一颜色在不同空间中的数字可能不同，不代表颜色凭空变亮或变暗。

线性空间意味着数值与光强成正比，适合做光照、颜色混合等计算。 它不是一个额外的后处理效果，而是这些计算所使用的数值表示方式。

2. 片元着色器生成颜色

片元 Shader 根据贴图、材质以及它所支持的光照等计算颜色。以 URP Unlit 为例，贴图与 _BaseColor 的基础关系是逐通道相乘：
$$
C_{\text{fragment}} = C_{\text{texture}}\odot C_{\text{BaseColor}}
$$

这属于染色，而不是直接相加

3. 形成相机颜色缓冲区

片元输出经过测试、混合等过程，写入相机颜色缓冲区。透明物体会与已有背景混合，因此一个像素不一定只代表一个物体。

  • 光栅化：把三角形覆盖的区域转换成片元，并生成深度、插值后的 UV 等数据。
  • 片元着色器：GPU 通常将多个片元分组、并行处理，计算片元的颜色等输出，也可以通过 discard 主动丢弃片元。
  • 深度测试、模板测试等操作：每个片元用自己的深度，与深度缓冲中对应位置的已有深度比较。因此，同一个三角形的片元可以有些通过、有些被遮挡；通过后，再按混合和写入设置更新帧缓冲。

GPU 不必等整个三角形的所有片元都着色完成，才开始深度测试和写入；这些阶段可以流水线式地重叠进行。

相机颜色缓冲区是 “帧缓冲中的颜色部分”，帧缓冲（Framebuffer）通常可以包含或关联：

  • 颜色缓冲：保存渲染出的像素颜色。
  • 深度缓冲：保存深度，用于判断遮挡等。
  • 模板缓冲：用于遮罩和限制绘制区域等。

4. 渲染管线执行 Post Processing

Post Processing 是对渲染结果进行处理的一组效果，例如 Bloom 是其中一种；其他效果还可能读取深度、运动信息等，而不只是颜色。
后处理还包括色彩调整、景深、运动模糊等，渲染管线读取前面得到的参数，并安排这些处理步骤。

Bloom 在屏幕显示之前处理渲染缓冲区，步骤可以概括为：

  1. 从相机图像中提取亮色。
  2. 对提取结果降采样、模糊。
  3. 放大并合并各层结果，形成扩散光晕。
  4. 让光晕参与原画面的合成。
    后处理通常把片元输出经过深度测试、透明混合等之后形成的 “相机颜色缓冲区” 作为输入，再处理成最终显示的画面。
    所以，它读取的是已渲染、但还没显示到屏幕上的图像，不是单个片元未经混合的输出，也不是屏幕显示完成后的截图。Bloom 就是对这张图像采样、提取亮色并模糊。

在 URP 的常规渲染流程下，Screen Space - Overlay 的 UI 通常不受相机的 Bloom 等后处理影响。
更直接的原因是：它在相机后处理完成后才叠加，Bloom 的输入图像里还没有这部分 UI。

顺序可以理解为：

  1. 相机渲染场景，得到颜色缓冲区。
  2. 按 Volume 配置执行 Bloom 等后处理。
  3. 再绘制 Screen Space - Overlay 的 UI。

Bloom 的 Threshold 计算

Bloom Inspector 输入的是 Gamma 空间阈值，URP 将它转换成线性阈值，再用于处理图像：
$$
T_{\text{linear}} = \operatorname{GammaToLinear}(T_{\text{Inspector}})
$$

输入 1 时，转换结果仍然是 1。阈值与图像不是各用一套空间直接比较，而是在该流程中使用线性值计算。

URP 14 使用固定 Soft Knee，且亮度指标取 RGB 最大通道。因此 Threshold 为 1 并不是 “所有不超过 1 的像素都剔除”：接近阈值的普通亮色也会贡献 Bloom，纯白 $(1,1,1)$ 就能产生光晕。
